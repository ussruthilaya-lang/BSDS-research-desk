# 4. Related Work

**4. Related work.** Research Desk draws on two bodies of work. The first is the distributed-systems material from the course on recovering from failure, ordering events and sharing work. The second is recent practice in multi-agent research systems, which are the workload this project sits underneath.

**Course readings.**

- **MapReduce** (J. Dean and S. Ghemawat, *Communications of the ACM*, 2008; HW2 Part I). The master re-runs the completed map tasks of a failed worker, because their output lives only on that worker's local disk, but it does not re-run completed reduce tasks, whose output is already in the distributed file system. Research Desk applies the same rule for the same reason. After each step a subagent writes its result to shared state, so a crashed worker's finished steps never run again and only the unfinished step is repeated. The difference is cost. A MapReduce task only computes, while a subagent step spends a call from a provider budget shared with every other job, so a repeated step is counted as a duplicate call in experiment E4.
- **Time, Clocks, and the Ordering of Events in a Distributed System** (L. Lamport, *Communications of the ACM*, July 1978, pp. 558-565; HW3 Part I). Separate machines share no clock, and "happened before" is the only order that events have for certain. Research Desk follows from this. Deadlines travel over HTTP as remaining time and never as clock times, times stored in shared state come from one clock (Redis's own), and only the gateway's clock paces provider calls.
- **Distributed Systems for Fun and Profit** (M. Takada; recommended text). A system model states what nodes and links can do and how they fail, and most real systems assume crash-recovery: a node fails only by crashing and may come back later. Research Desk assumes crash-recovery for its workers, and the leases and per-step checkpoints are built for it. It does not handle Byzantine faults and does not use a consensus protocol such as Paxos or Raft, which is future work.

**Outside material.**

- **How we built our multi-agent research system** (Anthropic Engineering, June 13, 2025; https://www.anthropic.com/engineering/multi-agent-research-system). A lead agent plans and starts 3-5 subagents in parallel, and "direct comparisons might need 2-4 subagents with 10-15 calls each". Early subagents "performed the exact same searches as other agents". The post says "Agents are stateful and errors compound", that Anthropic built systems that "can resume from where the agent was when the errors occurred", and that its lead agents run subagents synchronously, which "creates bottlenecks". The text read for this proposal does not mention provider rate limits. Research Desk starts where the post stops: it treats such a system as the workload and studies the backend problems of one shared budget, reuse across subagents, and recovery of a crashed subagent's work.
- **arXiv API terms of use** (https://info.arxiv.org/help/api/tou.html). For the legacy APIs, "no more than one request every three seconds" and a single connection at a time, applied to "all of the machines under your control as a whole", and a caller "should not attempt to overcome these limits by increasing the number of machines". The simulated provider models these limits, and the project never calls arXiv. The page also says the limits may change.
- **singleflight** (Go package `golang.org/x/sync/singleflight`; https://pkg.go.dev/golang.org/x/sync/singleflight). "A duplicate function call suppression mechanism", with calls grouped by a key. Its group is a value inside one program. Research Desk's merge of identical in-flight searches does the same job across several worker machines through shared state, and adds two things: the merged request keeps the latest waiter's deadline, and the claim on a search expires, so a dead claimant cannot block the waiters.
- **The Tail at Scale** (J. Dean and L. A. Barroso, *Communications of the ACM*, 56, 2013, pp. 74-80; https://research.google/pubs/the-tail-at-scale/). Its abstract says that temporary high-latency episodes, unimportant in a moderate-size system, "may come to dominate overall service performance at large scale". Only the abstract was read. It motivates experiment E3, which asks what one slow subagent costs the whole answer, and the gateway's deadline check, which uses a 95th-percentile latency estimate.
- **Model Context Protocol, architecture overview** (https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture.md). Local servers on the stdio transport "typically serve a single MCP client", while remote servers on the Streamable HTTP transport "will typically serve many MCP clients". Research Desk's public service uses Streamable HTTP because many users share it.

**Position.** The related work covers the agents on top (Anthropic) and the failure and ordering ideas underneath (MapReduce, Lamport, Takada), but none of the sources measures what a shared, rate-limited provider budget does to a fleet of subagents. Research Desk contributes a small, repeatable study of that layer: how a cache, merging of identical searches, a paced gateway with admission control, and task leases change throughput, cost and recovery when every provider call is metered.
