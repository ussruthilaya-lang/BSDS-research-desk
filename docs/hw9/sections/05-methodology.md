# 5. Methodology

**5a. Methods and approach.** Research Desk is built as six small services (job API, workers, gateway, provider simulator, MCP server and live control room) around one shared Redis store, and the same code runs on a laptop with Docker Compose and on a few AWS EC2 machines. The architecture diagram below shows the parts.

*One job, step by step.*

1. **Submit and admit.** A client sends a question and a deadline to the Job API. Admission control estimates the job's calls (N times k, less the calls expected to hit the cache), adds the calls already queued, multiplies by the three-second pacing gap, and rejects the job at once if that time exceeds the deadline. A rejected job spends no calls.
2. **Plan and fan out.** The lead turns the question into N subagent tasks, each a script of k searches, and puts them on a Redis task stream. In experiments the plan comes from a workload file. In the demo, Claude writes the plan.
3. **Search.** A free worker takes a task and, for each step, turns the query into a normalised key. It checks the cache, where a hit costs no provider call. If another worker is already fetching that key, it waits for that result and makes no second call. Otherwise it claims the key, with an expiry that it renews while the call is open, and sends the search to the gateway.
4. **Gateway.** One gateway is the only caller of the provider. It keeps a bounded queue, drops a request whose deadline can no longer be met (judged against a 95th-percentile latency estimate), starts calls at least three seconds apart with one call in flight, retries within a budget using backoff, and caps each user's share. The result goes into the cache and wakes every waiter.
5. **Checkpoint.** After each step the worker saves the step's result under the job, subagent and step. Writing the same result twice is harmless.
6. **Gather and brief.** The lead collects subagent results by one of two policies: wait for every subagent, or stop at the deadline minus a margin and use whatever has finished. The brief records its completeness, the share of subagents included.

*Failure handling.* A worker's lease is a heartbeat key that expires when the worker goes quiet. Another worker then takes the task and resumes after the last saved step. If the worker that holds a search's claim crashes, the claim expires and a waiter claims the search again. A merged search keeps the latest waiter's deadline, so one waiter giving up does not cancel the call for the others. A dropped search fails only its own subagent. Over HTTP, deadlines travel as remaining time, and only the gateway's clock paces calls.

*How AI is used.* The lead agent and subagents of a deep-research product are language-model agents, and Research Desk treats them as a workload. Measured runs replay scripted agents, so a run repeats exactly. Real Claude agents are used in the demonstration only. The backend is a live service reached through a thin Model Context Protocol (MCP) server over Streamable HTTP, behind a Cloudflare tunnel, so a person adds its address as a custom connector in Claude Desktop or with `claude mcp add` in Claude Code. A handle in the address identifies the caller for per-user quotas. There is no login, so a handle is not proof of identity. Two demonstration modes use the same service. In the first, Claude plans a question and starts a job through the MCP tools. In the second, several Claude subagents each call one search tool. Neither mode is ever part of a measured run, because real agents are not repeatable. The team builds the project with Claude Code; Section 2 covers its costs and benefits.

*Observability.* Every state change in every service is one structured event with a trace identifier, a run identifier, the client, the user, the job and the subagent, written to a log and to a Redis event stream, so one job's timeline can be rebuilt from its trace identifier. Prometheus counters cover jobs by status, tasks, searches by source (cache, merged or provider), merge waiters, answers served from an outdated corpus, gateway queue depth, calls and drops by reason, admission decisions, provider calls and violations, and lease expiries. A Grafana dashboard shows them over time. A live control room page shows the event stream as it arrives, with a status strip (violations, queue depth, calls a minute against the limit of 20, cache hit rate), a progress bar for every subagent, a timeline of the last 60 seconds of provider calls, worker leases, per-user usage, and a filterable event feed. Prometheus scrapes once a minute and Grafana refreshes at most every 5 seconds by default (both from their documentation), so experiments set a scrape interval of a few seconds, and the control room covers per-job progress. The provider simulator is the correctness alarm: it serves every call, counts overlap and pacing violations, and the count must be zero in every run.

*Feasibility.* A working prototype already exists: a discrete-event simulator, a seeded workload generator, a paced gateway with a bounded queue and deadline checks, workers and metrics, an Experiment 1 runner and an automated test suite. Full sweeps run on the simulator in seconds, and the deployed system confirms a few points of each. Real-time pacing makes a deployed run slow, so every service shares a time-scale setting (0.1 turns the three-second gap into 0.3 seconds). The scope is cut so that nothing ends half-done: scripted agents, read-only tools (searching is safe to cache and merge, while booking or sending is not), one gateway, and no consensus protocol. AWS use is limited to EC2 instances, with the Learner Lab credit balance logged before and after each session.

**5b. Experiments and tradeoffs.** Every setting runs with three seeds, and results report the median and the range. Each experiment has two parts: the full sweep on the simulator, and two or three confirming points on the deployed system, which replays the same workload file. A deployed point is compared with the simulator's number for the same workload, and any difference larger than 15 percent gets a measured explanation. The primary metric is correct, complete briefs finished on time per minute. Secondary metrics are provider calls per brief, wasted calls, 95th-percentile job latency, completeness, cache and merge hit rates, rejected, expired and failed jobs, recovery time and duplicate calls after a crash.

| # | Question | Sweep | Tradeoff evaluated |
|---|---|---|---|
| E1 | Where does throughput stop rising, and does admission control stop the collapse past that point? | workers {1, 2, 4}, arrival rate, admission {off, on}, no reuse | Accepting every job against rejecting early: fewer rejections against fewer wasted calls |
| E2 | How much do the cache and merging save, and when? | reuse {none, cache, cache plus merge}, subagents per job N {1, 3, 5, 10}, topic overlap within a job, skew across jobs | Memory and staleness against calls saved; waiting to merge against a duplicate call |
| E3 (simulator only) | Is a partial answer on time better than a complete answer late? | gather {wait for all, stop at the deadline}, provider slowdown {none, 2 times, 5 times} | Completeness against on-time rate |
| E4 | Does a crashed worker cost the job? | kill a worker mid-subagent; leases {off, on}; lease lengths 5, 10 and 20 seconds | Lease length: fast recovery against false takeovers that cause duplicate calls |

Experiments on fairness between wide and narrow jobs and on failover of the gateway are future work and are not promised. The workloads for these experiments, and what has been measured so far, are in Section 6.
